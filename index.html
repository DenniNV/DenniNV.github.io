Три системы, которые стоит посмотреть

01

Пулы с поведением и жизненным циклом

Runtime/CodePresets/Pools

Задача. Пули, гильзы и эффекты попаданий появляются и исчезают сотнями. Instantiate/Destroy дают мусор для GC и спайки кадра, а обычный пул решает только аллокации: когда вернуть объект, каждый скрипт решает сам — и где-нибудь забывает.

  • Жизненный цикл — часть контракта: IPoolable.OnRent / OnReturn. Прогретый объект сразу проходит OnReturn, поэтому новый и возвращённый всегда в одинаковом покое.
  • Когда вернуть, решает правило IReturnRule (Strategy): по времени, по окончании партиклов или вручную. У каждого слота своё состояние правила, правило выбирается в инспекторе через [SerializeReference].
  • Прогрев идёт пачками по 8 объектов с UniTask.Yield: большой пул не даёт спайк кадра на загрузке.
  • Потолок MaxCount: при переполнении переиспользуется самый старый активный объект, память не растёт.
  • Сегменты и ISourceSelector: один пул отдаёт несколько вариантов объекта. Пулы описаны в CMS, их id — сгенерированные константы PoolIds.

Почему так. В 0.3.2 я убрал время жизни пула по сцене: теперь все пулы глобальные, строятся и греются один раз на старте. Платим временем старта и памятью, получаем один жизненный цикл вместо двух и никаких пересозданий при смене сцены. Изменение помечено в CHANGELOG как BREAKING, с инструкцией по миграции.

02

CMS: данные для геймдизайнера, id для компилятора

Runtime/ContentManagerSystem · Editor/CodeGeneration

Задача. Контент игры — сцены, пулы, предметы — живёт в данных, а код ссылается на него по строковым id. Опечатка в строке проявляется только в рантайме, а переименование контента молча ломает ссылки.

  • CmsDatabase — ScriptableObject, который редактируется в CMS Editor. В рантайме Cms работает с копией, так что игра не портит ассет.
  • Кнопка Regenerate IDs запускает все генераторы. Они находятся через TypeCache, регистрировать ничего не нужно.
  • Новый генератор — наследник PartIdsGenerator<TPart> с двумя членами: имя класса и откуда брать id (Template Method). SceneIdsGenerator занимает 10 строк.
  • Генератор сортирует id и предупреждает о дублях. GeneratedCodeWriter пишет константы в отдельную папку AutoGenerated, руками её не правят.

Почему так. Геймдизайнер меняет данные, не трогая код, а программист получает ошибку компиляции вместо бага в рантайме: SceneIds.Game вместо строки "Game". Библиотека при этом не знает ни одного игрового id — игра добавляет свои генераторы рядом со своими частями CMS.

03

Точка входа: один предсказуемый запуск

Runtime/Core · DependencyInjection · CodePresets/State

Задача. В Unity инициализация размазана по Awake/Start десятков объектов: порядок не гарантирован, зависимости ищутся через синглтоны и FindObjectOfType, а каждая сцена тащит свои глобальные менеджеры.

  • Одна сцена Entry и один EntryPoint: поднимает провайдер Addressables, загружает ProjectContext, UIContext и ProjectDisposer и строит их строго по порядку через await.
  • Контекст — это скоуп DI, инсталлеры и билдеры. Скоуп живёт ровно столько, сколько объект контекста: SceneContext умирает вместе со сценой.
  • Дальше ведёт глобальная машина состояний: Initialize → LoadGameScene → InGame. Набор состояний подставляет игра через IGameStatesFactory на EntryPoint, библиотека про игру не знает.
  • Машина синхронная: переход завершается внутри SwitchTo, запрос из Activate встаёт в очередь, токен состояния отменяется до Release. Уход из состояния отменяет и начатую им загрузку сцены.
  • Один MonoBehaviour с Update прогоняет пайплайн групп в явном порядке. Принцип «сначала реши, потом действуй»: группа Brain (250) отрабатывает раньше Default (500), и системы в том же кадре читают уже устоявшееся состояние.

Почему так. Сначала машина состояний была асинхронной, и на время await игра оставалась «между» состояниями. В 0.3.2 я сделал её синхронной, а асинхронную работу привязал к токену состояния. Контракт закреплён EditMode-тестами: порядок Release и Activate, отмена токена до Release, очередь переходов.
